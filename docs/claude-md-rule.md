## Compaction marks (smart-compact)

- Pins: a line of your reply that starts with `◆ ` is carried verbatim through every compaction. Pinning is expected, not optional. In the reply where it first becomes known, write one `◆ ` line for each: an explicit constraint or preference the user set for the work, a final decision with its reason, a verified root cause or hard-won fact, an identifier that cannot be regenerated (deliverable path, ID). A reply that reports finished work whose request carried constraints ends with those constraints and the deliverable pinned. Do not pin intermediate scripts, exploration, attempts or transient state; compaction judges those against the current goal. A trivial question needs no pin. One self-contained line per pin, readable without the rest of the reply. If a pinned fact changes, write `◆✗ <distinctive fragment of the old pin>` and then the new pin.
- Discard marks: a line that starts with `◇ ` declares something certainly worthless from now on, whatever the next step turns out to be: a dead-end attempt, a throwaway script, output that a later result replaced. Name it in that one line, for example `◇ the three failed regex attempts above and their output`. The line and what it names are left out of the next compaction summary with no pointer. Mark only when you are certain; everything unmarked is still judged by the compaction policy, so when unsure, leave it unmarked. Never mark a user constraint, a decision, or anything pinned.
- Never start a line with `◆` or `◇` for any other reason. After a compaction, if you need a detail the summary lacks, run the recall command given right after the compaction with a few distinctive words; never Read or grep the transcript file itself, its lines are huge.
